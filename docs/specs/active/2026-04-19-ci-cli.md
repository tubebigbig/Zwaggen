# Spec — CI-mode CLI for batch + diff

## Problem

Zwaggen currently lives entirely in the browser. There is no way to exercise a spec file (run all its endpoints against a live server) or diff two spec files from a CI pipeline. Teams using Zwaggen as a source-of-truth for their API cannot:

- Smoke-test a deployment by pointing Zwaggen at a preview server and checking every endpoint responds as the spec claims.
- Gate a PR on "no breaking changes" by diffing `base/spec.json` against `head/spec.json` and failing the build when breaking entries appear.

Both of those are the TODO item "CI-mode CLI for batch + diff" under Feature.

## Goal

Ship a new executable — `zwag` — with two subcommands:

1. `zwag run <spec.json> [--base-url <url>] [--filter <regex>]` — iterate every endpoint in the spec, send an HTTP request, evaluate any per-endpoint assertions, print a pass/fail summary. Exit non-zero if any endpoint fails or any assertion fails.

2. `zwag diff <base.json> <current.json>` — diff two specs via the existing `diffSpecs` algorithm. Print breaking + non-breaking changes. Exit `1` if any breaking change is present; `0` otherwise.

## Success criteria

- `pnpm --filter @zwaggen/cli build` produces a runnable binary.
- From a shell: `node packages/cli/dist/cli.js diff examples/a.json examples/b.json` returns the expected exit code and output.
- `zwag run` on a spec pointed at a real HTTP server (including a local fixture server in tests) prints one line per endpoint (`PASS` / `FAIL`) and a final summary, and exits non-zero iff any endpoint failed.
- A `README.md` at `packages/cli/README.md` documents invocation, exit codes, and examples.
- `apps/web` continues to build and test identically; no imports in `apps/web` are changed this session.
- Unit tests in `packages/core` (copied test fixtures for diff + runner) pass. An integration test for `zwag diff` and `zwag run` (run points at a tiny in-process Node HTTP server) passes.

## Out of scope

- Migrating `apps/web` to consume `@zwaggen/core` (82 import sites across 52 files; file a follow-up TODO instead — "deduplicate apps/web + packages/core").
- Parallel execution of run (sequential is fine for MVP).
- Input injection for endpoints with required path/query/body params (handled by a placeholder strategy described below, not full user input).
- Secret injection (env-var-based basic flow; no config file).
- `--json` output format (plain text only for MVP).
- Publishing to npm (package is workspace-internal for now).

## Design

### Packages

Two new packages under `packages/`:

**`packages/core`** — pure, Node-compatible modules copied from `apps/web/src`:
- `src/schema/*` — types, diff, canonical, serialize, validate (whatever exists; see apps/web/src/schema/).
- `src/runner/*` — send, batch, assertions, auth, substitute, captures, path, classify-error.
- Public entry: `src/index.ts` barrel re-exporting the public API.
- `package.json` name `@zwaggen/core`, version `0.1.0`, private, `type: module`, `main: dist/index.js`, `types: dist/index.d.ts`.
- `tsup` build: `tsup src/index.ts --format esm --dts --out-dir dist`.
- Tests copied from `apps/web/tests/schema` + `apps/web/tests/runner` (the pure ones) and adapted to the new paths.

Files are **copied**, not moved. `apps/web` continues to own its copy. Dedup TODO is filed.

**`packages/cli`** — the `zwag` executable:
- `package.json` name `@zwaggen/cli`, `bin: { "zwag": "./bin/zwag.js" }`, depends on `@zwaggen/core` via `workspace:*`.
- `bin/zwag.js` is a two-line shim that `import('../dist/cli.js')`.
- `src/cli.ts` — commander-based entry with `run` and `diff` subcommands.
- `src/commands/run.ts` — the run implementation.
- `src/commands/diff.ts` — the diff implementation.
- Tests in `tests/` that spawn the CLI as a child process and assert exit code + stdout/stderr.

### `zwag diff` behavior

```
zwag diff <base.json> <current.json>
```

1. Read both files, parse JSON, pass to `fromJSON` (validates schemaVersion).
2. Call `diffSpecs(base, current)`.
3. Print the `breaking` list under a "Breaking changes" header (each entry: `[kind] location — summary`). Empty → print "No breaking changes." Same for `nonBreaking` under "Non-breaking changes".
4. Exit 1 iff `breaking.length > 0`, else exit 0.

### `zwag run` behavior

```
zwag run <spec.json> [--base-url <url>] [--filter <regex>]
```

1. Read spec file, `fromJSON`.
2. Determine base URL: `--base-url` flag overrides `spec.info.baseUrl`. If neither is set, exit with error.
3. Build the endpoint list. If `--filter <regex>`, keep only endpoints whose `${method} ${path}` matches.
4. For each endpoint (in declaration order):
   a. Build a `RunInputs` with defaults:
      - Path params: substitute `:name` with the literal string `1` (dumb smoke-test). Note this in output.
      - Query params: empty object.
      - Headers: empty object.
      - Body: omit (no body sent even if endpoint has requestBody).
   b. Call `sendRequest({ spec, endpoint, baseUrl, inputs, secrets: {}, useProxy: false })`.
   c. Evaluate assertions via `evaluateAssertions(result, endpoint.assertions)`.
   d. An endpoint passes iff the request completed (no network error, `result.errorKind == null`) AND every assertion passed. Otherwise fail.
   e. Print `PASS ${method} ${path} — ${status} in ${latencyMs}ms` or `FAIL ${method} ${path} — ${reason}`.
5. Summary line: `N/M endpoints passed`.
6. Exit 0 iff all passed, else 1.

The placeholder path-param strategy is intentionally dumb — this is a smoke test. Users who need real inputs can script around it later (future: `--inputs` JSON file).

### Secrets

For MVP, secrets (used by auth presets) are read from env vars whose names match the preset's conventional variable names. If an auth preset requires `BEARER_TOKEN`, the CLI looks up `process.env.ZWAG_BEARER_TOKEN`, etc. If the map is empty, `applyAuth` still works (it only injects what it has). Document in README. Full secret config is out of scope.

Actually, simpler MVP: the `secrets` argument to `sendRequest` is `{}` for the first version. Authentication is not wired through the CLI yet. Note this as a known limitation in the README, file a follow-up TODO.

### Error exit codes

- `0` — success
- `1` — one or more failures (test/assertion failed for run; breaking changes found for diff)
- `2` — CLI misuse (missing file, bad JSON, unknown subcommand, etc.)

### Dependencies

- `commander` — arg parsing. Add to `packages/cli/package.json`.
- `tsup`, `tsx`, `typescript`, `vitest`, `@types/node` — dev deps on both packages (match proxy package).

### Tests

**`packages/core/tests/`** — re-run the pure tests from apps/web (schema/diff, schema/canonical, runner/assertions, runner/classify-error). These already exist in apps/web; duplicate and adjust import paths. This confirms the copied code still works in the new package.

**`packages/cli/tests/`**:
- `diff.test.ts` — spawn `node dist/cli.js diff <fixture-a> <fixture-b>`, assert exit code + that expected lines appear in stdout.
- `run.test.ts` — start a tiny Node `http.createServer` on `localhost:0` (ephemeral port), create a minimal spec pointing at that URL with one endpoint that returns 200 and one that returns 500, spawn `zwag run`, assert the PASS/FAIL lines and exit code.

Tests assume the CLI has been built (`pnpm --filter @zwaggen/cli build`). The test script runs build first.

### What this spec explicitly does NOT do

- Move any files out of `apps/web`.
- Change any imports in `apps/web`.
- Add the CLI to `apps/web`'s build or tests.
- Publish anything to npm.
