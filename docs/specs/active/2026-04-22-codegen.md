# Spec — Codegen (TypeScript types + Zod schemas + typed client)

## Problem

Zwaggen's strategic value proposition is **the single API contract**: one `.zwag` spec authored by the team, consumed directly by both backend and frontend, no manual sync ritual. Today this promise is half-delivered:

- Backend can already consume a Zwaggen spec via the **OpenAPI export** (existing). Tools like NestJS, FastAPI, openapi-generator, etc. all consume OpenAPI fine.
- Frontend has **no clean consumption path**. To use a Zwaggen spec in TypeScript code today, a developer would have to read the spec by hand and re-type all interfaces. That's exactly the manual-sync workflow Zwaggen is supposed to eliminate.

The fix is **codegen**: a `zwag generate` CLI subcommand that walks a spec and emits TypeScript types, Zod runtime validators, and a typed API client object. Frontend devs commit the generated files (or run codegen on every build), import the typed client, and call APIs with full IDE autocomplete + runtime validation. The contract source is the `.zwag` file. The generated code is reproducible derived output.

This is the actual unlock for "single contract anywhere." It's also a strategic differentiator vs Bruno (request-first, no codegen) and vs raw OpenAPI tooling (codegen exists but no integrated editor + runner).

## Success criteria

### v1 (this spec)

- New CLI subcommand: `zwag generate ts <spec> [--out <dir>] [--client] [--watch]`
  - Reads a `.zwag` (or `.json`) spec file.
  - Emits TypeScript files into `--out` (default: `./zwaggen-generated/`).
  - With `--client`, also emits a typed client object.
  - With `--watch`, re-runs on spec change (uses `chokidar` or Node's built-in watch).
- Output files:
  - `types.ts` — pure TypeScript interfaces / type aliases for every Type in the spec, including extension-flattened shapes.
  - `schemas.ts` — Zod schemas matching every Type, exported as `z.ZodType` instances. Re-uses `import { z } from 'zod'` (consumer adds zod to deps).
  - `client.ts` (when `--client`) — typed client object: `client.tagName.endpointMethod(input): Promise<ResponseType>`.
- The generated output is **deterministic**: same spec input → byte-identical output (so commits are clean and CI diff comparisons work).
- The generated code is **universal**: works in browser, Node ≥ 18, Deno, Bun without changes (uses only `fetch`, `URL`, `URLSearchParams`, and Zod — all universal).
- The generated code has **zero runtime dependencies except `zod`** (consumer adds it; we don't bundle).
- Generated code is **readable**: well-formatted, includes `// AUTO-GENERATED — do not edit. Regenerate with: zwag generate ts ...` header, includes original Type/Endpoint description as TSDoc.
- An optional `zwag generate zod <spec>` subcommand emits ONLY the Zod schemas (for users who want runtime validation but not types/client — e.g., already type-generating from OpenAPI).
- Comprehensive unit tests covering: scalar types, object types, array types, union types, optional fields, type extension flattening, $ref resolution, edge cases (empty objects, recursive types if supported, enum types).
- One end-to-end integration test that: takes a representative `.zwag` spec, runs codegen, then `tsc --noEmit` on the output, then imports + uses the typed client against a fixture HTTP server, asserts the round-trip works.
- Docs: new `docs/guide/codegen.md` (en + zh-TW) explaining install, basic usage, watch mode, integration into a Vite/Next/etc project. Add link to the docs landing page.
- One TODO entry ticked: this spec.

### v1 ships independently of the desktop work

- No dependency on the desktop app, transport abstraction (P1), storage abstraction (P2), or any other prep item.
- Works against the existing `@zwaggen/core` Spec data structures as-is.
- Lives in `packages/cli` (or a new `packages/codegen` if it grows large enough to merit a split — decide during implementation).

## Out of scope (v1)

- **JS (untyped) output.** Defer to v2. v1 is TS-only because TS source compiles to whatever module format the consumer wants.
- **Pre-compiled npm package output** (per-spec npm packages with dual CJS/ESM). Defer indefinitely — consumers usually want generated code committed in their repo, not as a npm dep.
- **Multi-language codegen.** Python (Pydantic), Go, Rust, Java — all v3+. Each is its own spec when prioritized.
- **Backend handler stubs.** Express / Fastify / Hono / NestJS controllers generated from spec — different beast. v3+ at the earliest. Today backend uses the OpenAPI export; that path stays.
- **Pluggable templates.** A v2 feature. v1 emits one opinionated style; users who want different output write a feature request.
- **Per-endpoint runtime mocking** (auto-generated mock servers from spec). Different concern, separate spec if ever.
- **Codegen GUI inside the desktop / web app.** v1 is CLI only. The desktop app could later add a "Generate code…" button that wraps the CLI, but that's not v1.
- **Source maps for the generated code.** Generated code is the source for consumers; no source map needed.
- **Versioning of generated output across spec changes.** v1 just regenerates. Diff strategies (e.g., flagging breaking changes in generated types) come later if at all.
- **Tree-shakeable per-endpoint imports.** v1 emits one `client` object. v2 might emit per-endpoint exports.

## Approach

### CLI surface

```
zwag generate <generator> <spec> [options]

Generators (v1):
  ts        TypeScript types + Zod schemas + (optional) typed client
  zod       Zod schemas only

Common options:
  --out <dir>      Output directory (default: ./zwaggen-generated)
  --watch          Re-run on spec change

Generator-specific options (ts):
  --client         Also emit client.ts (typed client object)
  --no-types       Skip types.ts (use with --client to emit only schemas + client)
  --no-schemas     Skip schemas.ts (use only when consumer doesn't want runtime validation)
```

Existing `zwag` subcommands are untouched. `zwag generate openapi` and `zwag generate jsonschema` (already exist) move under the same `generate` namespace if not already there — verify during implementation.

### Output shape — types.ts

For a spec like:

```yaml
# (conceptual — actual spec format is JSON)
types:
  User:
    fields:
      id: string
      name: string
      email: string?  # optional
  Admin:
    extends: [User]
    fields:
      role: 'admin' | 'super-admin'
```

The generated `types.ts`:

```typescript
// AUTO-GENERATED by zwag — do not edit. Regenerate with: zwag generate ts <spec>

export interface User {
  id: string;
  name: string;
  email?: string;
}

export interface Admin extends User {
  role: 'admin' | 'super-admin';
}
```

Multi-parent extends flatten via TypeScript intersection types when needed.

### Output shape — schemas.ts

```typescript
// AUTO-GENERATED by zwag — do not edit. Regenerate with: zwag generate ts <spec>
import { z } from 'zod';

export const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  email: z.string().optional(),
});
export type User = z.infer<typeof UserSchema>;

export const AdminSchema = UserSchema.extend({
  role: z.enum(['admin', 'super-admin']),
});
export type Admin = z.infer<typeof AdminSchema>;
```

Note: when both `types.ts` and `schemas.ts` are generated, the types in `types.ts` are the canonical export; `schemas.ts` re-derives types via `z.infer` for users who want them locally. To avoid type-name collisions across files, consumers import explicitly: `import type { User } from './types'` vs `import { UserSchema } from './schemas'`.

### Output shape — client.ts (with --client)

```typescript
// AUTO-GENERATED by zwag — do not edit. Regenerate with: zwag generate ts <spec> --client
import { z } from 'zod';
import { UserSchema, type User } from './schemas';

export interface ZwaggenClientOptions {
  baseUrl: string;
  fetch?: typeof globalThis.fetch;  // override (e.g., for testing or interception)
  headers?: Record<string, string> | (() => Record<string, string>);  // static or dynamic auth
}

export function createClient(opts: ZwaggenClientOptions) {
  const f = opts.fetch ?? globalThis.fetch;
  const baseHeaders = () => typeof opts.headers === 'function' ? opts.headers() : (opts.headers ?? {});

  return {
    users: {
      async list(): Promise<User[]> {
        const r = await f(`${opts.baseUrl}/users`, { headers: baseHeaders() });
        if (!r.ok) throw new ZwaggenHttpError(r);
        return z.array(UserSchema).parse(await r.json());
      },
      async create(input: User): Promise<User> {
        const r = await f(`${opts.baseUrl}/users`, {
          method: 'POST',
          headers: { 'content-type': 'application/json', ...baseHeaders() },
          body: JSON.stringify(input),
        });
        if (!r.ok) throw new ZwaggenHttpError(r);
        return UserSchema.parse(await r.json());
      },
      // ... more endpoints
    },
    // ... more tags
  };
}

export class ZwaggenHttpError extends Error {
  constructor(public response: Response) {
    super(`HTTP ${response.status} ${response.statusText}`);
    this.name = 'ZwaggenHttpError';
  }
}
```

Endpoints group by tag (or fall back to `default` if untagged) so the client tree mirrors how endpoints are organized in the spec UI.

### Path parameter substitution

Endpoints with path params like `/users/{id}` translate to client method signatures: `client.users.get({ id: string }): Promise<User>`. The generator emits a small inline `joinPath` helper or template-literal substitution.

### Query / header / body input shape

Endpoints have a structured input: `{ path?, query?, headers?, body? }`. The generated method takes a single input object with only the relevant sub-shapes (e.g., a GET-only endpoint with no path params has an empty input object: `client.users.list(): Promise<User[]>`).

### Universality (browser + Node + Deno + Bun)

- `fetch` — global in Node ≥ 18, browser, Deno, Bun. ✓
- `URL` / `URLSearchParams` — global everywhere. ✓
- `JSON` — universal. ✓
- `zod` — supports all four runtimes, ESM + CJS via dual exports. ✓

No imports of `node:*` modules in generated code. The CLI itself uses Node modules (fs, path, chokidar) — that's fine; the GENERATED code is universal.

### Module format of generated code

Generated `.ts` files use ESM syntax (`import` / `export`). Consumer's tsconfig (or bundler) decides what comes out. This works for:
- TS projects with `"module": "esnext"` / `"nodenext"` / `"node16"` (modern)
- TS projects with `"module": "commonjs"` (TypeScript transpiles ESM → CJS)
- JS-only projects: emit-then-tsc or run through a bundler

If we ever need pre-emitted JS, that's the v2 `zwag generate js` subcommand with `--module cjs|esm|both`.

### Determinism

- Stable iteration order: walk types and endpoints in spec-declaration order, not Object.keys order (which is insertion-order in modern JS but should be belt-and-braces).
- Stable string formatting: use a fixed quote style (single), trailing commas always-on, spacing rules pinned.
- Pipe through `prettier` programmatically with a frozen config — guarantees identical output across machines and OS line-ending settings.
- Regression test: generate twice, byte-compare.

### Testing strategy

- **Unit tests** (vitest): one suite per generator (ts, zod, client). For each: fixture spec → run generator → string-compare against frozen expected output. Snapshot-style with explicit fixtures (not `expect(...).toMatchSnapshot()` magic — explicit `.expected.ts` files reviewable in PRs).
- **Integration test**: take a real spec (e.g., the existing `petstore.zwag` if one exists, or create a small one), run codegen, run `tsc --noEmit` on the output, assert no errors. Then start an HTTP fixture server (simple Node http server returning canned responses), instantiate the generated client against it, exercise list + get + create + delete, assert the client returns correctly typed values.
- **Determinism test**: run generator twice, byte-compare outputs.
- **Watch mode test**: write a fixture spec, start watch, modify spec, assert regeneration fires within a reasonable timeout.

### Package structure

Decide during implementation:

- Option A: add to `packages/cli` directly. New `packages/cli/src/generate/` directory with one file per generator. Smallest diff.
- Option B: new `packages/codegen` with the generator logic, consumed by `packages/cli`. Cleaner separation if codegen grows. Bigger diff.

Default Option A; refactor to Option B if/when codegen exceeds ~1000 LOC or when adding non-TS generators (Python etc).

## Risks

- **Spec → TS type fidelity gaps.** The spec may have types that don't cleanly map to TS (e.g., recursive types, deeply nested unions). Mitigation: tests cover all current `@zwaggen/core` Type variants; if a gap surfaces, document the limitation and either generate `unknown` with a TODO comment or fail the generator with a clear error.
- **Zod ↔ TS type drift.** A Zod schema might infer slightly different types than the TS interface emitted alongside it (e.g., readonly arrays, branded types). Mitigation: pick ONE source of truth per file. types.ts has hand-written interfaces; schemas.ts uses `z.infer` re-export so consumers get one type definition either way. Test that `z.infer<typeof UserSchema>` is structurally equivalent to the `User` interface for representative types.
- **Tag-based grouping when endpoints have no tag.** Default to a `default` namespace; document this. Avoid name collisions.
- **Reserved TS keywords as field names** (e.g., a spec field literally named `class`). Generator escapes with quoted property names where needed: `interface Foo { 'class': string }`. Test fixture covers this.
- **Universal fetch in Node ≥ 18 only.** Consumers on Node 16 (EOL) need to provide a polyfill via `opts.fetch`. Documented in the codegen guide.
- **Watch mode debouncing.** Rapid spec edits could trigger redundant regenerations. Use a 200ms debounce.
- **Determinism failures across OS / pnpm versions.** Prettier handles most of this; pin prettier version in `packages/cli/package.json` and lock its config.
- **Generator output growing the consumer's repo diff.** First-time codegen on a large spec produces a lot of generated lines. Mitigation: encourage `.gitignore`-then-CI-regenerate workflow as one of the documented patterns; or commit it and accept the noise. Let users pick.
