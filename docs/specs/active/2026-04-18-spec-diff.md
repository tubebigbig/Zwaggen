# Spec diff — find breaking changes between two spec files

**Status**: draft
**Date**: 2026-04-18
**Area**: `apps/web` — new `schema/diff.ts`, new `DiffPanel`, `AppHeader`

## Problem

"Spec in git" is the story. The natural question is "what did this PR change?" Git diff on the raw JSON answers *literally* but not *semantically* — a reordered `endpoints` array blows up the diff without meaning anything, and a renamed type looks like a delete + add. Users want a categorized, human-readable "what changed, and is it breaking?" view.

## Goal

Load a second `.zwaggen.json` alongside the current one, run a pure `diffSpecs(a, b)`, and render a categorized panel: Endpoints added / removed / changed; Types added / removed / changed; breaking changes highlighted.

## Non-goals

- **Not a full structural diff.** We don't surface every whitespace change — just the semantic ones that affect API consumers.
- **Not `git blame`-level commit history.** Two specs compared; git does the rest.
- **Not auto-fetch from remote.** User picks the two files manually — they know which revision matters.
- **Not PR integration / CI output.** Spec-diff is an in-app affordance MVP. A CLI or GitHub Action could wrap it later.
- **Not automatic "migration guide" generation.** We categorize, we don't prescribe fixes.
- **Not diff-across-multiple-specs in one view.** Two at a time.
- **Not a union of types across specs** (e.g., merge or rebase semantics). One is "base", one is "current".

## Requirements

1. `diffSpecs(a: Spec, b: Spec): SpecDiff` — pure, deterministic, no I/O. Returns categorized change records.
2. **Endpoints** are matched by `method + path` (NOT `id` — ids change between edits, method+path is the API contract). Endpoints present only in `a` → removed; only in `b` → added; in both with any meaningful change → changed.
3. **Types** are matched by name. Same logic.
4. **Changes classified as breaking or non-breaking**:
   - Endpoint removed → breaking.
   - Endpoint added → non-breaking.
   - Endpoint changed:
     - A new required param (path/query/header) → breaking.
     - A param that used to be optional becoming required → breaking.
     - Request-body type narrowed (e.g., a field became required, or enum shrunk) → breaking.
     - Response type changed in a way that narrows what the server promises → breaking (caller's code may assume the old shape).
     - New optional param → non-breaking.
     - Description changed → non-breaking.
     - New response status added → non-breaking.
   - Type removed → breaking IF it was referenced by any endpoint; else non-breaking (orphan deletion).
   - Type field removed → breaking.
   - Type field added as `required: true` → breaking.
   - Type field added as `required: false` → non-breaking.
   - Enum shrunk (values removed) → breaking.
   - Pattern tightened (new `pattern` where there was none, or stricter regex) → breaking.
5. **Report format**:
   ```ts
   export interface SpecDiff {
     breaking: ChangeEntry[];
     nonBreaking: ChangeEntry[];
   }
   export interface ChangeEntry {
     kind: string;                // e.g. 'endpoint.removed', 'type.field.required-added'
     location: string;            // 'POST /users' or 'types:User.email'
     summary: string;             // human-readable one-liner
   }
   ```
6. **UI**: a "Compare spec" action in `AppHeader` opens a file picker for the other spec. On load, show a modal with two sections (Breaking / Non-breaking), each a list of `ChangeEntry` rendered with color-coded chips. Summary header: "N breaking, M non-breaking changes".
7. The current spec is always `b` (the "after"); the picked file is `a` (the "before"). So "removed" entries are things in `a` missing from the current spec.
8. No persistence. Diff is a one-shot view.

## Design

### Diff engine — `apps/web/src/schema/diff.ts` (new)

```ts
import type { Spec, Endpoint, TypeDef, ObjectField, ParamDef } from './types';

export interface ChangeEntry {
  kind: string;
  location: string;
  summary: string;
}

export interface SpecDiff {
  breaking: ChangeEntry[];
  nonBreaking: ChangeEntry[];
}

export function diffSpecs(a: Spec, b: Spec): SpecDiff;
```

Internal structure:

```ts
function diffSpecs(a: Spec, b: Spec): SpecDiff {
  const breaking: ChangeEntry[] = [];
  const nonBreaking: ChangeEntry[] = [];

  // 1. Endpoints: match by method+path
  diffEndpoints(a, b, breaking, nonBreaking);

  // 2. Types: match by name
  diffTypes(a, b, breaking, nonBreaking);

  // 3. Info/environments/auth: skip — not API-consumer-facing.

  return { breaking, nonBreaking };
}
```

**Endpoint matching**: `const key = (e: Endpoint) => `${e.method} ${e.path}``. Build `aMap: Record<key, Endpoint>` and `bMap: Record<key, Endpoint>`. Iterate keys; categorize present-in-a-only / present-in-b-only / present-in-both.

**Endpoint change detection** for endpoints in both:

- Compare each param list by `name`:
  - New param with `required: true` → breaking, kind `endpoint.param.required-added`.
  - Removed param → breaking if it was required, else non-breaking.
  - Param type changed → breaking (conservative default).
  - Param required flag flipped false→true → breaking.
  - Param required flag flipped true→false → non-breaking.
- Compare `requestBody`:
  - `a` had body, `b` doesn't → non-breaking (server got more permissive).
  - `a` didn't, `b` does → breaking (new required body).
  - Both present, type changed → breaking (conservative).
- Compare `responses`:
  - Response status added in `b` → non-breaking.
  - Response status removed → non-breaking (the server could still return it, but we no longer document validation — treat as doc loss, not contract break).
  - Response type changed for an existing status → breaking (caller's type assumptions).
- `description` changed → non-breaking, kind `endpoint.description.changed`.
- `tags` changed → non-breaking.

**Type change detection** for types in both:

- Kind changed (e.g. `object` → `union`) → breaking.
- Object:
  - Field removed → breaking.
  - Field added `required: true` → breaking.
  - Field added `required: false` → non-breaking.
  - Field required flag flipped false→true → breaking; true→false → non-breaking.
  - Field type changed (structural or `ref` target change) → breaking.
- String:
  - `enum` shrunk (values removed) → breaking.
  - `enum` grown → non-breaking.
  - `pattern` added or changed to a different regex → breaking.
  - `minLength` increased or `maxLength` decreased → breaking.
- Number:
  - `min` increased or `max` decreased → breaking.
  - `enum` shrunk → breaking.

Deep type equality: since `TypeDef` is structural, use `JSON.stringify` equality as the coarse check; when unequal, emit `type.changed` as breaking without drilling further. A full structural diff is a future enhancement; for MVP the coarse check is sufficient and never misses a real change.

**Kind strings** are stable, hierarchical, and documented:

- `endpoint.removed` (breaking)
- `endpoint.added` (non-breaking)
- `endpoint.description.changed` (non-breaking)
- `endpoint.tags.changed` (non-breaking)
- `endpoint.param.required-added` (breaking)
- `endpoint.param.required-flipped-to-true` (breaking)
- `endpoint.param.required-flipped-to-false` (non-breaking)
- `endpoint.param.removed` (breaking if was required, else non-breaking)
- `endpoint.param.type.changed` (breaking)
- `endpoint.requestBody.added` (breaking)
- `endpoint.requestBody.removed` (non-breaking)
- `endpoint.requestBody.type.changed` (breaking)
- `endpoint.response.added` (non-breaking)
- `endpoint.response.removed` (non-breaking)
- `endpoint.response.type.changed` (breaking)
- `type.removed` (breaking if referenced, else non-breaking)
- `type.added` (non-breaking)
- `type.kind.changed` (breaking)
- `type.field.removed` (breaking)
- `type.field.added.required` (breaking)
- `type.field.added.optional` (non-breaking)
- `type.field.required-flipped-to-true` (breaking)
- `type.field.required-flipped-to-false` (non-breaking)
- `type.field.type.changed` (breaking)

### UI — `apps/web/src/ui/DiffPanel.tsx` (new)

Modal triggered from `AppHeader`. Open flow:

```ts
async function openDiff() {
  const h = await pickOpen(); // or uploadFile fallback
  if (!h) return;
  const { text } = await readFile(h);
  let other: Spec;
  try { other = fromJSON(JSON.parse(text)); }
  catch { alert(t('diffBadJson')); return; }
  setDiffBase(other);
}
```

`diffBase` state → render `<DiffPanel base={diffBase} current={spec} onClose={...} />`.

Panel content:

- Header: "{{breakingN}} breaking, {{nonBreakingN}} non-breaking changes"
- Two sections with colored chips:
  - Breaking (red background, sorted by `kind` then `location`)
  - Non-breaking (slate background)
- Each row shows `[kind chip] location — summary`.

## Testing

### Unit — `apps/web/tests/schema/diff.test.ts` (new)

Required cases (one `it` per kind string):

- Identical specs → empty diff.
- Endpoint added → one non-breaking entry.
- Endpoint removed → one breaking entry.
- Endpoint description changed → one non-breaking entry.
- Required param added → breaking.
- Required param removed → breaking.
- Optional param added → non-breaking.
- Param required-flag flipped both ways.
- Param type changed → breaking.
- Request body added → breaking.
- Request body removed → non-breaking.
- Request body type changed → breaking.
- Response status added → non-breaking.
- Response status removed → non-breaking.
- Response type changed for shared status → breaking.
- Type added → non-breaking.
- Type removed but unreferenced → non-breaking.
- Type removed AND referenced by an endpoint in the other spec → breaking.
- Type kind changed (object → union) → breaking.
- Object field removed → breaking.
- Object field added required → breaking.
- Object field added optional → non-breaking.
- Field type changed → breaking.

## Error handling

- Invalid JSON or wrong-shape file: `fromJSON` throws a `SpecVersionError` or generic parse error. Alert and abort.
- `schemaVersion` mismatch between the two specs: proceed anyway (diff doesn't depend on version), but surface a warning at the top of the panel.

None. Future enhancements: hierarchical drill-down on `type.changed`, per-endpoint diff summaries in the endpoint list, CLI mode for CI.
