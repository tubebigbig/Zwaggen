# Spec — PWA offline docs

**Status:** active
**Date:** 2026-04-19
**Scope:** `apps/docs` only. The playground at `apps/web` (`play.zwaggen.com`) is out of scope.

## Goal

Make `docs.zwaggen.com` installable as a PWA and fully usable offline. Once the user has visited the site once, the entire docs corpus (both locales, all screenshots, client-side search index, Mermaid renderer) should work without a network connection.

## Motivation

The docs are pure static content — no server-side rendering, no live API calls. Users who read tutorials on planes, on the subway, or behind captive portals get no value from an always-online site. Precaching the whole corpus on first visit (~2 MB) is cheap and unlocks the full reference offline.

## Non-goals

- Offline functionality for the playground (`apps/web`) — it makes live network calls by design.
- Serving outbound links (GitHub, `play.zwaggen.com`) offline — they fail gracefully.
- Push notifications, background sync, or any non-caching PWA feature.
- Versioned archival of old docs — service worker always reflects latest deploy.

## Architecture

Introduce `vite-plugin-pwa` into the VitePress build. The plugin writes:

- `sw.js` — Workbox-generated service worker that precaches the build output.
- `manifest.webmanifest` — installability metadata.
- `registerSW.js` — tiny client script that registers the SW and exposes update events.

A small addition to the VitePress custom theme imports the registration script and renders an update-toast component. The custom theme currently does not exist in `apps/docs/.vitepress/` — it must be scaffolded alongside this work.

No server changes: Cloudflare Pages serves the generated files as-is. The `_headers` file already in `apps/docs/public/` keeps working.

## What gets cached

**Precache** (injected into SW manifest at build time, all fetched on first visit):

- All HTML pages — 13 English + 13 zh-TW = 26 routes.
- JS, CSS, and font bundles emitted by VitePress.
- Client-side local search index.
- Mermaid runtime and its dependencies.
- `/screenshots/*.png` — 13 files, ~1.4 MB total.
- `favicon.svg`, manifest, PWA icons.

Total budget ceiling: **5 MB**. Build fails if precache exceeds this (`maximumFileSizeToCacheInBytes` configured accordingly). Current estimate: ~2 MB.

**Runtime cache** (stale-while-revalidate):

- Any CDN-hosted fonts, if added later. Nothing today.

**Never cached:**

- External origins (GitHub, `play.zwaggen.com`). They route through the network; offline users see normal browser offline error when clicking them.

## Manifest + icons

`manifest.webmanifest` (generated by plugin):

```
name:             "Zwaggen Docs"
short_name:       "Zwaggen"
start_url:        "/"
scope:            "/"
display:          "standalone"
theme_color:      "#4f46e5"
background_color: "#ffffff"
icons: [
  { src: "/favicon.svg",    sizes: "any",     type: "image/svg+xml", purpose: "any maskable" },
  { src: "/pwa-192.png",    sizes: "192x192", type: "image/png" },
  { src: "/pwa-512.png",    sizes: "512x512", type: "image/png" }
]
```

`favicon.svg` already exists at `apps/docs/public/favicon.svg` (indigo rounded square, white Z polyline).

The PNG icons (`pwa-192.png`, `pwa-512.png`) are generated once from the SVG by a small Node script at `apps/docs/scripts/gen-icons.mjs` using `sharp`. The script runs manually when the SVG changes (not in CI). Generated PNGs are committed to `apps/docs/public/`. Rationale: keeps the build pipeline simple (no `sharp` native dep on Cloudflare Pages) and the SVG changes rarely.

`<link rel="icon">`, `<link rel="manifest">`, and `<meta name="theme-color">` are injected into `<head>` via VitePress's `transformHead` config hook.

## Update flow

`vite-plugin-pwa` uses `registerType: 'prompt'` — a new service worker installs silently but does **not** take control until the user consents.

When `onNeedRefresh` fires, a Vue component in the VitePress theme shows a bottom-right toast:

- English: **"New docs available."** [Refresh]
- zh-TW: **"有新版文件可用。"** [重新整理]

Clicking Refresh calls `updateSW()` → `skipWaiting()` → full page reload. A close button dismisses the toast without updating; it reappears on the next visit if still out of date.

Toast styling: matches VitePress default theme variables (`--vp-c-bg`, `--vp-c-brand`). Locale is detected from the current URL (`/zh-TW/` prefix → Chinese, else English).

## Testing

### Build verification

- `pnpm --filter docs build` succeeds with no new warnings.
- `dist/sw.js` and `dist/manifest.webmanifest` exist.
- The precache manifest inside `sw.js` lists all 26 HTML files, the search index, and `/screenshots/*.png`.

### Runtime verification (local)

- `pnpm --filter docs preview`
- Chrome DevTools → Application tab:
  - Service Worker registered and activated.
  - Manifest parsed with no errors; icons resolve.
  - Lighthouse PWA audit passes (installable + offline categories).
- Network tab → toggle **Offline** → reload: every page still renders, including screenshots and Mermaid diagrams.
- Visit an un-visited page while offline (e.g., load `/`, go offline, navigate to `/guide/openapi-import`): page loads from precache.

### Update-flow verification

- Build v1, serve via preview, load in browser.
- Change a page, build v2, redeploy preview.
- Reload the tab: the update toast appears. Clicking Refresh loads v2.

### Install verification

- Desktop Chrome: install icon appears in address bar; installing opens in standalone window.
- Mobile (Chrome Android / Safari iOS): "Add to Home Screen" shows the Zwaggen icon and opens without browser chrome.

## Deployment

No changes to the release or deploy pipeline. Cloudflare Pages serves the new files on next push to `main`. The existing `_headers` file already long-caches hashed assets; the SW handles precache invalidation client-side via content hashes baked into the SW build.

## Risks and mitigations

- **Stale cache after deploy.** Mitigated by `registerType: 'prompt'` — users see the refresh toast within seconds of opening the tab on a new deploy. The SW itself is served with `no-cache`, so browsers always check for a new SW.
- **Precache budget creep.** The screenshots dominate. If future docs add large images, the 5 MB ceiling fails the build and forces a runtime-cache strategy instead.
- **Search index size.** VitePress local search index grows with content. If it ever exceeds a few hundred KB, consider excluding it from precache and letting it load lazily (still cacheable via runtime cache).
